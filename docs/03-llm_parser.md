# llm_parser.py 详解 —— LLM 解析 + 确定性后处理

## 这个文件为什么存在

规则解析(parser.py)对没见过的表达无能为力:"今晚八点前回公司"、"顺路去药房买药"、"菜鸟驿站"。LLM 天然擅长理解口语,所以引入可选的 LLM 解析器。

但这里有一个关键设计判断:**不能把正确性交给模型自觉**。LLM 会漏字段、编错时间、把"取快递"误判成预约。所以整个文件是"LLM 生成 + 确定性后处理修复"的架构——模型只负责"理解",规范由代码兜底。

## 三层回退架构

```
prefer_llm=True 且配了 Key?
  ├─ 是 → llm_parse_line(一行) → 成功就用 LLM 结果
  │        失败(没key/网络错/返回垃圾) → 回退 parse_line 规则解析
  └─ 否 → parse_line 规则解析
```

`parse_with_llm` 是**逐行**回退,不是整段回退:10 行任务里 8 行 LLM 解析成功、2 行失败,那 2 行用规则,其余保留 LLM 结果。

## SYSTEM_PROMPT 设计要点(调优的重头)

Prompt 里把规则解析器积累的所有口径都写进去了,和 parser.py 保持同一套语义:

- **只输出 JSON,不要解释、不要 markdown 围栏**——好解析;
- **字段规则逐条定义**:day 偏移、时间用"当天第几分钟"、12 小时制 +12、固定预约动词清单、优先级关键词、时长口径表(开会 60/取快递 20/银行 30)、地点规范词(建设银行→银行);
- **明确负面规则**:"取快递/取件/收件不是预约,不要用 fixed_min"——这是最容易错的点,单独强调。

## 重点函数逐个说明

### `llm_available()` —— 有没有配置

同时要求 Key 和 BaseURL 都非空,避免配了一半导致每次都失败。

### `_extract_json(content)` —— 从模型回复里抠 JSON

LLM 经常不守规矩输出 ```` ```json ... ```` 围栏或前后废话。函数剥掉围栏,取**第一个 `{` 到最后一个 `}`**,失败返回 None(触发规则回退)。

### `_to_int(value, lo, hi, default)` —— 带范围校验的整数转换

把模型输出的字符串/浮点转成 int,超出合法范围就回默认值。`day` 限制 0-6、`priority` 1-3、`duration` 10-600。**模型说什么就信什么是大忌,这里全部加了边界**。

### `canon_place(place, text)` —— 地点归一(确定性修复)

- 模型给了品牌名(招商银行)→ 含"银行"归一为"银行";
- "药房/药店"→"药店","驿站/快递"→"快递驿站";
- 模型没给地点但文本里有"接孩子/放学" → 补"学校";
- 属于规范关键词表(`CANON_PLACES`)就原样保留。

### `canon_duration(text, duration, earliest, latest)` —— 时长口径兜底

银行类业务(办卡/取钱/存钱...)模型常给 60 或 20,统一修正为 30。但**如果用户写了明确起止时间段**(9 点到 12 点),时长按段长,不覆盖——这是和 parser.py 完全一致的口径。

### `_normalize(text, data)` —— 模型输出 → 任务字典(核心)

把模型返回的 JSON 转成和 parser.py 完全一致的任务结构,并做三层确定性兜底:

1. **兜底 3**:只有模糊时段(上午/下午)没具体几点 → 复用 parser 的 `vague_period` 时段窗口;
2. **兜底 2**:文本是取快递/取件但模型误标了 `fixed` → 改回时间窗(earliest=fixed, latest=fixed+180);
3. **兜底 1**:模型给了 earliest 但漏了 latest → 补默认 3 小时窗口。

顺序很讲究:先处理模糊时段,再修取快递误判,最后补窗口,避免互相覆盖。

### `llm_parse_line(text, timeout=30)` —— 单行 LLM 调用

- `temperature=0`:解析任务要确定性,不要创造性;
- 任何异常(网络错、超时、JSON 解析失败、结构不对)全部吞掉返回 None → 走规则回退,**解析失败绝不能崩掉整个请求**;
- 这里不做批量调用,是刻意的:一次一行,失败粒度最小。

### `parse_with_llm(text, prefer_llm=False)` —— 按行解析整段文本

入口函数。逐行执行"LLM 优先、规则兜底"的策略,返回任务列表。

## 为什么评测要"规则不调优、只调 LLM 路径"

`benchmark_llm.py` 的设计基线:规则解析是固定对照组,**不随 LLM 的调优而改动**。这样评测结果反映的是"LLM 相对规则的真实增益",而不是"我把规则也一起改了所以更好"。这是实验设计上的自觉,写报告/面试时值得主动讲。
