# main.py 详解 —— 命令行入口

## 这个文件为什么存在

Web 版需要 Flask + 高德 Key + 浏览器,调试成本高。CLI 版把核心链路(解析 → 求解 → 输出)压缩成一条命令行:

```bash
python main.py
# 输入任务, 每行一个, 空行结束
# 明天上午9点去银行办卡
# 下午3点去学校接孩子放学(重要)
# (回车)
# → 打印推荐顺序
```

**零外部依赖**:只 import `parser` 和 `optimizer`,不碰 geocode/route/高德——坐标是写死的默认起点,距离用直线估算。CLI 的价值是:
1. 快速验证算法逻辑(不配 Key、不开服务器);
2. 演示最小闭环:自然语言 → 结构化 → 最优顺序;
3. 作为 `optimizer.py` 的配套 demo(两个文件 `__main__` 里都有类似演示)。

## 重点函数逐个说明

### `to_hhmm(minute)` —— 分钟 → "HH:MM"

把"第 900 分钟"显示成 "15:00",配合 `divmod` 取小时和分钟。

### `fmt_task_list(arrivals)` —— 结果格式化

把 `optimize_route` 返回的 arrivals 变成多行可读文本:序号、地点、优先级(低/中/高)、到达时间、停留时长。优先级映射用字典 `{1: "低", 2: "中", 3: "高"}`,比 if-elif 干净。

### `read_tasks()` —— 命令行输入

每行一个任务,空行结束,返回 `\n` 连接的文本——和 Web 端"多行文本输入"共用同一套解析入口(`parse_tasks` 按行切)。

### `main()` —— 主循环

```
输入 → parse_tasks → optimize_route → 打印顺序和成本统计 → 问"继续?(y/n)"
```

`ValueError`(锁定冲突等)捕获后提示错误继续,不崩。这个循环结构演示了"解析失败/求解失败"都应该被拦在业务层。

## 与 Web 版的关系

- 同一套核心代码(`parser` + `optimizer`),CLI 和 Web 只差"输入方式和展示层";
- 这验证了分层设计:算法模块不依赖 Flask,可以被任何入口复用(CLI/Web/测试/benchmark 都在 import 它们)。

## 演进建议

如果以后做算法实验,可以把 CLI 升级成"数据集评测入口"(读文件 → 批量跑 → 输出 CSV),比 `benchmark.py` 的随机生成更适合针对真实场景调参。
